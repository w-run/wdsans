## 三、同步到 w-pc：改用哈希校验

### 发现：文件大小不可靠

改 fsSelection 只改 OS/2 表里的**几个字节**，
新旧 TTF 大小可能完全相同（如 Bold 都是 20.92MB），靠大小比对会误判。

**改用 sha256。**

### 结果：15/15 哈希一致

| 产物 | 大小 | 哈希 |
|---|---|---|
| 7 档 TTF | 20.91–20.98 MB | ✓ 全部一致 |
| 7 档 WOFF2 | 7.48–7.93 MB | ✓ 全部一致 |
| VF WOFF2 | 20.01 MB | ✓ 一致 |

## 四、TTF 传输仍用 gzip

| 方式 | 每档耗时 |
|---|---|
| TTF 直传 | ~100s |
| TTF + gzip | 7–69s（多数 50–70s）|

WOFF2 本身已压缩，直传 32–43s/个。

## 六、教训

**「大小相同」不等于「内容相同」。**

元数据修正是字节级替换，几乎不改变文件大小。
验证产物一致性必须用哈希，不能用大小或时间戳。

这与 P37 的「口径混淆」是同类问题的两面：
- P37：两个数字不同 ≠ 有一个错（口径问题）
- P41：两个文件大小相同 ≠ 内容相同（精度问题）

**都要看「比的是什么」，而不是只看「比出来一样不一样」。**
