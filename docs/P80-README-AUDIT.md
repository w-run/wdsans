### 2.3 新增：tnum 限制（P78）

这是用户必须知道的可用性限制：

```
5. 数字不等宽、无 tnum 特性：数字为比例宽度（362–587 unit），
   表格数字列不会自动对齐。上游 Mona 原本提供 tnum/pnum，
   拉丁合并时未移植；补齐需 10 个等宽数字变体字形，

```

## 四、意外收获：闸门抓到一个真问题

改完 README 后，用 **package 模式**跑交付闸门：

```
模式: package
  !! 缺少必需文件: OFL.txt
  !! README 引用了不存在的文件: OFL.txt
交付完整性: 2 个问题
```

### 这是一个真实的交付缺陷

| 位置 | 有 OFL.txt 吗 |
|---|---|
| w-pc `dist/`（最终交付包）| **有** |
| w-box `wdsans-dist/`（构建产物）| **没有** |

**这意味着：如果从 w-box 重新打包交付，会缺少许可证文件。**

而 OFL 1.1 明确要求分发时必须附带许可证全文。

### 修复

把 OFL.txt 补到 w-box 产物目录，再跑：

```
模式: package
  引用存在: OFL.txt
交付完整性: 通过
```

### 这正是 P74 双模式改造的价值

P74 加 `mode="build"/"package"` 时，我的目的是**消除构建噪音**。

没想到它顺带带来了一个能力：**可以用 package 模式随时做交付终检**。

如果只有一种模式（且构建走 build），这个「产物目录缺 OFL」的问题
**永远不会被自动化发现**。

## 五、教训

### 1. 文档过时是「渐进式」的

每一次小的交付变更（加 VF、加子集、改名）都只改局部，
没人回头更新总数。

累积下来：
- 文件数 16 → 29（差 81%）
- 体积 220.4 → 247.6 MB
- 文档 28 → 84 份

**「总数」类字段最容易过时，因为它依赖全局统计，而每次改动都是局部的。**

### 2. README 应该由脚本生成「事实部分」

本轮我手改了一遍，但下次重建后又会过时。

**正确做法**：把「文件清单 + 大小 + 合计」做成脚本自动生成，
人只写「说明性文字」。

这是后续该做的事（本轮先记录）。

### 3. 修文档时顺手跑闸门，常有意外收获

本轮本来是「审 README」，结果闸门报出「产物目录缺 OFL.txt」。

**审文档的过程，天然会触发对交付物完整性的重新检查。**
