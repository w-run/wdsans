# P89：文档一致性闸门（第七道）

## 承接 P88 的待办

P88 手工把三次自我更正的结论回填到旧文档，留下一个问题：

> 文档已达 93 份，手工核对开始吃力，且以后每次更正都要重做一遍。

本轮把它做成自动闸门。

## 一、设计：登记表 + 扫描

核心是一份「已推翻结论」登记表，每项含四个字段：

| 字段 | 含义 |
|---|---|
| 关键词正则 | 被推翻的说法长什么样 |
| 说明 | 为什么被推翻 |
| 更正出处 | 哪份文档做了更正 |
| 允许出现 | 哪些文档可以出现该关键词（= 更正文档本身）|

### 当前登记的四项

| 关键词 | 真相 | 出处 |
|---|---|---|
| 子集丢了 GDEF | 无组合标记时的正常闭包裁减 | P86 |
| GPOS 丢失 / 8→6 | 特性数恒定 5，未丢失 | P86 |
| format 14 丢失 | 需变体选择符在字符集内 | P87 |
| 字形槽位为 0 | 有 10037 个未引用槽位，但均不可回收 | P79 |

### 判定逻辑

```python
for 每份 P*.md:
    if 文件名在「允许出现」列表: 跳过
    if 命中被推翻关键词:
        if 全文含更正标记（「更正」/「已推翻」/「观察属实」等）:
            视为已标注，通过
        else:
            报警
```

## 二、阴性测试（必做）

按既定原则，新闸门必须有阴性测试。造一份含 4 项旧说法、无更正标记的假文档：

```
!! P999-FAKE.md 含已推翻结论「子集丢失 GDEF（实为无组合标记时的正常闭包裁减）」但未标注更正（见 P86）
!! P999-FAKE.md 含已推翻结论「子集 GPOS 丢 mark/vkrn（实为特性数恒定 5，未丢失）」但未标注更正（见 P86）
!! P999-FAKE.md 含已推翻结论「子集 format 14 丢失（实为需变体选择符在字符集内）」但未标注更正（见 P87）
!! P999-FAKE.md 含已推翻结论「字形槽位为 0（实为有 10037 个未引用槽位，但均不可回收）」但未标注更正（见 P79）
检出问题数: 4 -> **有效**
```

对照组（同一内容 + 加「P86 更正」标记）：

```
文档一致性: 通过
问题数: 0 -> 正确
```

**4/4 全部检出，对照组正确通过。**

### 为什么这个阴性测试特别重要

第一次跑真实文档时结果是「通过 / 问题数 0」。

**「0 问题」有两种可能**：

| 可能 | 含义 |
|---|---|
| 文档确实都标注了 | 闸门正常 |
| **正则根本没命中任何东西** | **闸门失效但看不出来** |

只有阴性测试能区分这两者。本轮证明了是前者。

## 三、已接入构建（第七道闸门）

| 7 | **`doc_gate`** | **已推翻结论必须标注更正** |

## 四、这个闸门的特殊之处

前六道闸门检查的都是**产物**（字体文件、README）。

第七道检查的是**文档之间的一致性**——这在字体项目里不常见。

### 为什么字体项目也需要它

本项目有一个特殊情况：**文档本身就是交付物的一部分**。

- 用户要求「文档不是一成不变的，需要实时验证、实时更新」
- 93 份编号文档记录了大量判断，其中 3 次是**自我推翻**
- 若旧文档不更新，后来者会读到互相矛盾的结论

**当「结论会演进」成为常态时，文档一致性就需要自动检查。**

## 五、教训

### 1. 「0 问题」的闸门必须验证

这是 P70 就确立的原则，本轮再次应用。

新闸门第一次跑真实数据就返回「通过」，如果直接收工会很危险——
**一个正则写错的闸门，永远返回通过。**

### 2. 登记表是让「知识演进」可维护的关键

如果不做登记表，每次更正后只能靠人记住「哪些结论被推翻了」。

做成表之后：

| 好处 | 说明 |
|---|---|
| 可累积 | 新更正只需加一行 |
| 可检查 | 闸门自动扫描全部文档 |
| **自带上下文** | 每项都写明了「真相是什么、出处在哪」|

### 3. 这个模式可以推广

「登记已推翻的结论 + 扫描未标注的使用」不限于本项目：

```
任何长期演进的文档体系都适用：
  技术决策记录（ADR）
  事故复盘
  研究笔记
```

**关键是把「什么是错的」显式化，而不是只记录「现在什么是对的」。**
