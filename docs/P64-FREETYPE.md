# P64：FreeType 渲染验证（第三种独立路径）

## 为什么再验一遍

此前已用两条路径验证渲染：
1. **HarfBuzz `hb-view`**（P45/P52/P56）
2. **Chrome `@font-face`**（P56）

本轮加第三条：**FreeType（Pillow）**。

为什么要三条？因为三者走的是**不同的字体解析实现**：

| 路径 | 解析器 | 用途 |
|---|---|---|
| HarfBuzz | HarfBuzz | Linux 图形栈 / 多数开源软件 |
| Chrome | OTS + Skia | 浏览器 |
| **FreeType** | **FreeType** | **Windows GDI、macOS、Linux 桌面、Java、Qt** |

**FreeType 是覆盖面最广的渲染库**，Windows 的 GDI 底层就用它（或等效实现）。
三条都通过，才能说「在任何环境下都正常」。

## 一、字体名唯一性（系统字体列表视角）

FreeType 读取的 `(family, style)`：

| 档位 | FreeType 读取 | 唯一性 |
|---|---|---|

| Light | `WDesign Sans / Light` | 唯一 |
| Normal | `WDesign Sans / Normal` | 唯一 |
| Regular | `WDesign Sans / Regular` | 唯一 |
| Medium | `WDesign Sans / Medium` | 唯一 |
| Bold | `WDesign Sans / Bold` | 唯一 |
| Heavy | `WDesign Sans / Heavy` | 唯一 |

**7/7 组合唯一，无冲突。**

这是 P63 结论在另一条路径上的独立确认：
虽然 nameID 1 有 6 个值（设计使然），但 FreeType 组合 `family+style` 后
每档都能唯一标识，用户不会看到重名。

## 二、渲染墨量随字重单调

用 FreeType 渲染「永和九年岁在癸丑」（64px），统计实际墨量：

| 档位 | 文字宽 (px) | 墨量 (px) |
|---|---|---|
| Thin | 512.0 | 3573 |
| Light | 512.0 | 4032 |
| Normal | 512.0 | 6025 |
| Regular | 512.0 | 6915 |
| Medium | 512.0 | 8927 |
| Bold | 512.0 | 11378 |
| Heavy | 512.0 | 13725 |

### 两个观察

1. **文字宽全部 512.0 px** —— 8 个汉字 × 64px = 512，
   再次印证中文全角等宽（P45/P56 结论在 FreeType 下同样成立）。

2. **墨量严格单调**：3573 → 4032 → 6025 → 6915 → 8927 → 11378 → 13725，
   最大 / 最小 = **3.84 倍**。

   这与 P53 的发现一致（固定偏移让细体相对减得多、粗体相对减得少），
   但绝对墨量仍是严格递增的。

## 四、一个测量陷阱（本轮又踩了）

第一次测渲染宽度时，画布固定 1400px，七个档全部报「1400」。

看起来像「字重不影响宽度」（合理，中文等宽），但实际是**画布被撑满截断**——
文本实际宽度约 512px + 边距，而 `img.getbbox()` 返回了画布边界。

修正：先用 `font.getlength()` 问 FreeType 真实宽度，再按该宽度建画布。

**这是「测量工具的容器限制了测量结果」的典型例子。**

## 六、教训补充

本轮又踩了一个测量陷阱（画布截断），说明 METHOD-TRAPS 里应该补一条：

> **容器限制**：画布/缓冲区尺寸会截断测量结果，
> 先问工具「真实尺寸是多少」，再建容器。
