# P82：从「自动化事实」到「不该写的事实」

## 承接 P81

P81 建了 `gen_readme_facts` 闸门，第一次跑就报出：

```
!! 文档份数: README 84 != 实际 85
```

我改了 85。

**然后本轮结束时再跑，又变成 85 != 86。**

因为这一轮又新增了 P81 这份文档。

## 一、这不是执行失误，是结构性问题

```
写 P80 文档 → 文档数 84→85 → README 写 84（当轮已过时）
写 P81 文档 → 文档数 85→86 → README 写 85（当轮又过时）
```

**只要「文档数」写进 README，它必然永远是错的**——
因为写 README 这个动作本身不产生文档，
而写文档这个动作会改变数字。两者永远差一步。

## 二、更深一层：这个数字该不该出现在交付 README 里

| 问题 | 分析 |
|---|---|
| 用户关心吗 | **不关心**。他们拿到的是字体，不是我们的开发过程 |
| 会变吗 | **每轮都变** |
| 补上它有价值吗 | 无。README 已说明「详细文档见 docs/」，读者自己去看即可 |

**结论：这是一个不该出现在交付文档里的内部指标。**

## 三、修复有两层

### 3.1 内容层：从 README 移除精确份数

```diff
- 详细设计文档与逐轮实测记录见 w-box `/workspace/wdsans/docs/`（85 份编号文档）。
+ 详细设计文档与逐轮实测记录见 w-box `/workspace/wdsans/docs/`，按 P 编号归档、持续增补。
```

改为定性描述。**信息量没减少**（读者知道去哪看），但不再有易变数字。

### 3.2 闸门层：从「校验它」改为「禁止它」

```python
# 改前：校验份数是否正确
if int(m.group(1)) != docs:
    problems.append("文档份数: README %s != 实际 %d")

# 改后：发现精确份数就报警
if re.search(r"（(\d+) 份", text):
    problems.append("README 不应包含精确的编号文档份数（该指标持续变化）")
```

**这是闸门语义的转变**：

| 阶段 | 闸门职责 |
|---|---|
| P81 | 「你写的数字对不对？」|
| P82 | 「这个数字你压根不该写。」|

## 四、验证

```
退出码=0
```

## 五、这一轮真正学到的东西

### 自动化不是终点，它有时会反过来告诉你「这项根本不该自动化」

路径是：

```
P80  手动改数字（漏了一处）
  ↓
P81  写脚本自动校验（立刻抓出偏差）
  ↓
P82  校验了两次都失败 → 意识到这个字段本身不该存在
```

**如果没做 P81 的自动化，我不会连续两次撞到同一个问题，**
也就不会想到「这个数字不该写」这一层。

### 「可维护」有时意味着「删掉」，而不是「自动维护」

面对一个总是过时的字段，有两种反应：

| 反应 | 评价 |
|---|---|
| 写脚本每次重算 | 治标。仍要人记得跑脚本 |
| **判断它是否该存在，不该就删** | **治本** |

本轮先做了前者（P81），撞了两次墙后才想到后者（P82）。

**这是合理的探索顺序**——但要能识别出「该换思路了」的信号。

那个信号就是：**同一个问题反复出现，说明修复的层次不对。**

## 六、README 事实闸门最终保留的检查项

| 项 | 该写吗 | 检查方式 |
|---|---|---|
| 七档 TTF 大小 | **该**（用户需要知道体积）| 与实际文件比对 |
| 文件数 29 | **该**（清单完整性）| 统计实际文件 |
| 总体积 247.6 MB | **该**（下载决策依据）| 累加字节 |
| VF.woff2 大小 | **该** | 同 TTF |
| ~~编号文档份数~~ | **不该**（内部指标、持续变化）| **禁止出现** |
