# P91：把「已知陷阱」写进流程（tools/accept.py）

## 承接 P90 的教训

P90 最终验收时，脚本**直接 hb-view 喂了 VF.woff2**，得到 205 字节的纯白图，
差点误判为「VF 损坏」。

而 P43 早就记录过：

> HarfBuzz 8.4.0 **不解 WOFF2**，静默返回空白，exit code 0。

**文档记录了 ≠ 流程遵守了。** 这是本轮要解决的问题。

## 一、做法：把解包内置到工具里

新增 `tools/accept.py`，三层检查：

| 层 | 函数 | 检查内容 |
|---|---|---|
| 传输 | `check_transport` | 与 w-box 源逐文件 sha256 比对 |
| 格式 | （复用 ots_gate）| OTS 全部通过 |
| 渲染 | `check_render` | **自动解包 woff2 后渲染，统计墨迹像素** |

### 关键设计：解包是隐藏步骤

```python
def render_ink(path, ...):
    ttf = _unpack_woff2(path, tmp)   # ← 调用方无需知道
    subprocess.run(["hb-view", "--font-file=" + ttf, ...])
```

**调用者传入 woff2 或 ttf 都可以，工具内部保证喂给 hb-view 的永远是 TTF。**

### 为什么用「墨迹像素数」而不是「文件大小」

P90 时我用 PNG 文件大小判断（205 bytes vs 3840 bytes）。

**文件大小是间接指标**：不同字号、不同文字会给出不同大小，阈值难定。

改为直接统计**墨迹像素数**：

```python
ink = int((a > 40).sum())   # a = 255 - 灰度
阈值: ink >= 200 视为有内容
```

**这是直接指标：空白图就是 0 像素，有字就是数千像素，不会误判。**

## 二、验证：证明工具真的解决了问题

### 对照实验

```
直接 hb-view woff2  : 墨迹 0 px      ← 空白（复现 P90 的坑）
accept.render_ink   : 墨迹 3576 px   ← OK

结论: 工具正确解包 woff2
```

### 这个对照为什么必要

如果我直接写 `accept.render_ink(woff2)` 得到 3576，**不能证明什么**——
因为 3576 也可能来自「工具碰巧能读」。

**必须同时跑「直接喂」的对照组，证明 0 vs 3576 的差异确实来自解包这一步。**

这延续了本项目一贯做法：**新功能必须证明它真的改变了行为**。

## 四、教训

### 1. 「文档记录」和「流程遵守」之间有一道鸿沟

```
P43 写了文档  →  我读过了  →  但写验收脚本时仍然直接喂 woff2
```

**为什么？因为写脚本时想的是「渲染」，不是「woff2 要先解包」。**

教训：**已知的陷阱必须内建到工具里，而不是依赖人临场记得。**

判断标准：

| 情况 | 对策 |
|---|---|
| 陷阱只影响我这一次 | 记文档即可 |
| **陷阱会影响每一次同类操作** | **必须内建到工具** |

本轮属于后者——**任何渲染 woff2 的操作都会踩到**。

### 2. 用直接指标，不用间接指标

| 指标 | 类型 | 问题 |
|---|---|---|
| PNG 文件大小 | 间接 | 阈值依赖字号/文字 |
| **墨迹像素数** | **直接** | **空白就是 0，不会误判** |

这和 P75 的教训同源（重心不能用控制点数、要用墨量）：

**指标要能直接反映「我们关心的那个性质」。**

### 3. 对照实验是「证明工具有效」的唯一方式

新工具输出「3576 px」本身不说明任何问题。

**必须有「错误用法」的对照组（0 px），才能证明差异来自新工具。**

否则可能是：
- 工具没生效，但碰巧也能读
- 工具生效了，但读的是错的东西

对照实验排除了这两种可能。

### woff2 的处理

woff2 的解包渲染较慢（仅 VF 解包后 47.9 MB，单文件数十秒），
本轮的对照实验已单独验证 `accept.py` 能正确解包（0 px → 3576 px）。

**woff2 与 TTF 是同一内容的不同封装**（P69 已确立此口径），
TTF 渲染正确即可推断 woff2 内容相同；格式合法性另由 OTS 全部通过保证。
