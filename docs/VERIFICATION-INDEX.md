## 九、被推翻的认知（重要）

本项目中**多次出现「数据看起来像缺陷，实为正常」**的情况。记录在此，避免重蹈。

| 现象 | 初步判断 | 实际结论 | 出处 |
|---|---|---|---|
| 字重递进非线性（+5/+20/+8）| 档位分配不均，需改 avar | **Noto 增量完全相同**，基座设计 | P47 |
| 减细比率 0.750→0.908 不等 | 减细不均匀 | **差值恒 11-12**（σ=0.5），固定偏移的正常表现 | P53 |
| 横竖比 0.946 ≠ Noto 1.018 | 比例被破坏 | **光学补偿**，OPPO 0.932 / 鸿蒙 0.945 同区间 | P54 |
| 零面积字形 11 个 | 轮廓塌缩 | **全是空白字符**，与 Noto 清单完全一致 | P55 |
| 中文字宽全部相同 | 字体未生效 | **汉字全角等宽**，任何字体都一样 | P45 / P56 |
| 基线差 −12px | 中英基线错位 | **汉字 overshoot**，拉丁底部精确 0.0 | P58 |
| hb-shape 测 woff2 正常 | woff2 可用 | **Hb 8.4.0 不解 woff2**，返回 gid0 静默 | P43 |
| 删除 Mac name 记录无影响 | 可安全删 | **连带删掉了 ID0/ID7**，违反 OFL | P49 |

**共同教训：孤立看数据容易误判，必须对比参照字体 + 选对度量口径。**

### 已知限制（P78）

| 项 | 状态 | 影响 | 替代方案 |
|---|---|---|---|
| 数字等宽 / tnum | **缺**（10,037 未引用槽位全是独立汉字，回收即违反铁律）| 表格数字列不对齐 | CSS `font-variant-numeric` + 等宽回退 |

说明：Mona 原本提供 `tnum`/`pnum`/`frac`，拉丁合并时未移植；
补它需 10 个新字形（`zero.tf`…`nine.tf`）。
**P79 更正**：原以为「槽位为 0」，实为 10,037 个未引用槽位；
但抽查 300 个，**0 个与已映射字形重复**——全是基座独立汉字（异体/竖排变体），
回收会丢失覆盖，等同违反「不删字形」铁律。结论不变，依据已修正。

本轮对索引里的关键数字做了**自动化核对**：

```
OK   cmap 44905           -> 44905
OK   glyphs 65535         -> 65535
OK   typo 880/-120/0      -> (880, -120, 0)
OK   win 1160/288         -> (1160, 288)
OK   hhea 1000/-200       -> (1000, -200)
OK   vhea 500/-500        -> (500, -500)
OK   USE_TYPO 未置位      -> 0b1000000（bit7=0）
OK   主TTF 7个            -> 7
OK   主WOFF2 8个          -> 8（7 档 + VF）
OK   子集TTF 6个          -> 6
OK   子集WOFF2 6个        -> 6
OK   主TTF 20.91-20.98MB  -> 20.91-20.98
OK   七档WOFF2 7.48-7.93  -> 7.48-7.93（VF 20.01 单列）
```

**13/13 与产物实际值一致。**

### 一处差点误报

第一次核对时脚本报 `主WOFF2 7.48-20.01 MB`，看着像文档错了。
实际是脚本用 `*.woff2` 通配把 VF（20.01MB）也算进去了。
把 VF 排除后范围正是 7.48-7.93，**文档没问题，是脚本口径错**。

又一次印证：**核对本身也要正确选口径**，否则会造出假警报。
