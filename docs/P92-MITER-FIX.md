## 二、斜边失真：找到真因

### 测量方法

按边的方向分箱，统计「减细后 / 减细前」的边缘长度比。

### 修复前的数据

| 边角度 | 比值 | 判定 |
|---|---|---|
| 横 0-10° | 0.9615 | 正常 |
| 浅斜 10-30° | **0.8266** | **过度收缩 17%** |
| 斜 30-60° | **1.1481** | **反而变长 15%** |
| 陡斜 60-80° | 0.9459 | 偏移 |
| 竖 80-90° | 0.9222 | 正常 |

**同一个减细参数，斜边既有的被过度收缩、有的反而被拉长。**
这就是「曲线怪、粗细不均」的直接来源。

### 第一次修正：错的

我先以为是 `d` 的取值问题，改成连续加权：

```python
t = abs(ny)
d = d_h * (1 - t) + d_v * t
```

**实测证明无效**：斜 30-60° 仍是 1.1527（原 1.1481）。

而且这个式子本身是错的：水平边 `ny=1 → t=1 → d=d_v`，
但水平边本该用 `d_h`。**映射反了。**

### 真因：角点用法向「矢量和」

```python
out[k] = seg[k] + d1 + d2      # d1/d2 是相邻两条边的法向位移
```

**矢量和只在 90° 角成立。** 数学上：

| 内角 | 矢量和给出 | 正确斜接 | 超出 |
|---|---|---|---|
| 90° | 2d·cos45° = 1.414d | d/sin45° = 1.414d | 正确 |
| 135° | 2d·cos22.5° = 1.85d | d/sin67.5° = 1.08d | **1.71 倍** |

钝角处严重超出 → 斜边被「推出去」→ 表现为边变长。

### 正解：求相邻偏移线的交点

```python
lines[k] = 边 k 按自身法向平移后的直线
out[k]   = lines[k-1] 与 lines[k] 的交点
```

对任意角度精确；并加 3×max(d_h,d_v) 的位移上限，防锐角处交点飞出。

## 五、关于 glow-sans 算法能否直接移植

我读了 `vendor/glow-src/src/glyph-manipulate/` 下的：
`detect-ends.js`、`detect-feet.js`、`PostFilters.js`（含 removeFeet /
strokeEndsFlatten / hookTension / softenDots）。

**结论：无法直接移植。** 复刻成 Python 后在 10 个典型字上测出：
笔末 0、钩 0、点 0，全部未命中。

### 根因：点结构不同

```
Noto「一」字真实轮廓：
  ON(44,431) ON(959,431) ON(959,349) ON(44,349)   ← 4 点全 ON

glow-sans detectEnds 要求 6 点模式：
  [off, on, off, off, on, off]
```

glow-sans 处理的是「栅格化 → CV 骨架 → 重描边」产生的**稠密曲线**；
Noto 原生 TTF 是**稀疏矩形**表示。

**判据必须重写**（按几何形状识别笔末/钩/点），不能照搬点序模式。

## 六、教训

### 1. 我的第一次「修正」是错的，靠实测才发现

改连续加权后我本可以直接宣布「已修复」。

但重新测了斜边比值，发现 **1.1527 vs 1.1481 几乎没变**。

**「改了代码」不等于「修了问题」——必须重测同一个指标。**

### 2. 真正的原因常在「我以为不是问题」的地方

我一直盯着 `d` 的数值，把「矢量和」当成理所当然的正确做法。

实际上矢量和是「近似」，只在直角成立。

### 3. 用户的眼睛比我的指标灵敏

用户看截图就说「曲线很怪、粗细不均」。

而我的所有闸门（面积、重心、墨量）**全部通过**——
因为它们都是聚合指标，对局部畸变不敏感。

**「斜边长度比」这个指标是我被批评后才想到要测的。**

它本该是标准检查项。
