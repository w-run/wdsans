## 缺陷

ratio-analysis 队友报告「9 个字形 advance 错位」。我复核后确认，
并发现实际是 **138 个**，远超其报告的 9 个。

受影响字符（节选）：i j 9 : ; " ) ] } < ` ¡ 等

## 根因

`advance_fix2.run()` 的工作列表构建方式：
```python
for cp, mname in mcm.items():
    if mglyf[mname].numberOfContours <= 0:
        continue            # <-- 跳过了复合字形
```
即只修了 Mona 侧为**简单轮廓**的字形。但 i/j/9/引号/括号在 Mona 里是**复合字形**，
它们的 hmtx base 一直是**未缩放的 Mona 原值**，而 HVAR delta 已按 0.895 烘焙 → 曲线错位。

## 关键证据：400 档偏差恒为 -12/-13
```
i  215 vs 227 (-12)      "  329 vs 342 (-13)
j  209 vs 222 (-13)      9  562 vs 575 (-13)
```
恒定的 -12/-13 正是 (1 - 0.895) 的缩放误差，直接指向「未乘 sx」。

## 修复

新增 wds/advance_fix3.py：去掉 numberOfContours 过滤，改用码位配对，
只要求目标字形在我方存在且有轮廓。修复 138 个字形。

验证 @400 全部归零：i/j/9/:/;/"/)/]/}/< 十个字形全部 ours == 目标。

## 遗留：中间字重的插值误差（可接受）

| wght | 中位偏差 | 最大偏差 | >5 的字符数 |
|---|---|---|---|
| 250 | 0 | 0 | 0 |
| 300 | 2 | 8 | 9 |
| 350 | 1 | 7 | 1 |
| 400 | 0 | 0 | 0 |
| 500 | 2 | 7 | 3 |
| 700 | 4 | 16 | 27 |
| 900 | 0 | 0 | 0 |

**我们采样的三个锚点（250/400/900）偏差全为 0**，中间档有非线性插值误差。
原因：本字体 HVAR 只有 2 个 region（peak 在 250 与 900），而 Mona 的真实 advance 曲线
经 avar 映射（0.2->0.279、0.6->0.639）后是非线性的，两 region 只能线性插值。

这是双 region HVAR 的固有精度限制，不是逻辑错误。
彻底解决需增加 HVAR region，会显著增大体积。**判定为可接受。**

排版影响实测：AV/Ty/rm/i9/Hamburg/quotation 在 700 档全部无粘连。
