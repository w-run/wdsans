## 四、过程中的一个重要发现

### 第一次渲染：VF 四行全空白

第一次做验收图时，VF 的四行**完全没有文字**，连中文都没有。

看起来像 VF 坏了。但这是**工具限制，不是字体问题**：

```
VF.woff2 (原文件)     输出 205 bytes   ← 空白
VF 解包后 TTF         输出 3840 bytes  ← 正常
VF TTF wght=700      输出 3830 bytes  ← 正常
```

**205 字节的 PNG 就是一张纯白图。**

### 与 P43 记录一致

P43 早已记录：

> HarfBuzz 8.4.0 **不解 WOFF2**——返回 `[gid0=0+500|gid0=1+500]`，
> exit code 0，**静默失败**。所有 hb 测试必须用 TTF。

本轮再次撞上同一个坑，但**因为记得这条记录，立刻转向解包验证**，
没有误判为「VF 损坏」。

### 这也说明验收流程需要一个前置步骤

```
错误做法：直接 hb-view *.woff2  → 得到空白 → 以为字体坏了
正确做法：woff2 → 解包成 TTF → 再渲染
```

**浏览器能解 WOFF2，HarfBuzz CLI 不能。这是工具差异，不是字体缺陷。**

## 七、教训

### 1. 验收必须分层，每层用对工具

| 层 | 工具 | 能发现什么 |
|---|---|---|
| 传输 | sha256 | 文件错位/遗漏 |
| 格式 | OTS | 表结构非法 |
| 渲染 | hb-view / 浏览器 | 字形缺失/排版错乱 |

**三层缺一不可**：哈希一致的坏字体仍能通过传输层；
OTS 通过的字体仍可能渲染异常。

### 2. 已知的工具陷阱要写进流程，而不只是写进文档

P43 记录了「HarfBuzz 不解 WOFF2」，但这次验收脚本**仍然直接喂了 woff2**。

**文档记录了 ≠ 流程遵守了。**

正确做法：验收脚本里内置「woff2 先解包」这一步，
而不是依赖人记得。

### 3. 最终验收的价值在于「用交付物本身」

前面 30 多轮做的都是**单项指标测量**（厚度、重心、收尖…）。

本轮不同：**直接拿用户会拿到的那些文件，跑完整链路**。

这是唯一能发现「单项都对、但组合起来有问题」的方式。
