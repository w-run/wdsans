# P44：文档与产物一致性核查（系统化）

## 背景

P43 发现 hb 不解 woff2，暴露出「文档里可能有基于错误前提的结论」。
于是做了一次**系统化扫描**：提取产物实测值，反查所有文档。

## 一、产物实测基准（唯一事实来源）

```
cmap        44,905
glyphs      65,535
typo        880 / -120  gap 0
win         1160 / 288
hhea        1000 / -200
vhea        500 / -500
fsSelection 0b01000000（bit6=1, bit7=0）
```

## 二、发现的问题（2 处真实错误结论）

### 问题 1：CONTRACT.md 声称已置 USE_TYPO_METRICS

原文档（已决项，标 `[x]` 完成）：
> 修复行高：hhea/typo 对齐 880/-120，**置 USE_TYPO_METRICS**，vhea 500/-500

**实测产物 `fsSelection` bit7 = 0，未置位。**

P24 已查明不置位的原因（置位会让拉丁下伸 −193 与 `〱〲` −542 跨行重叠，
Noto 与 OPPO 同样不置位），但 CONTRACT 没同步更新。

**已修正**：加注说明「原计划置位，实测后决定不置位」，并指向 P24。

### 问题 2：P8 声称「woff2 hb-view 渲染成功」

原文：
> WOFF2 可解码：Thin 解码后 17 表 / 44810 cmap / 65535 glyph，**hb-view 渲染成功**。

**P43 已证实 Hb 不解 woff2，当时的「渲染成功」实为空白。**

**已修正**：保留「fontTools 可解码」的正确部分，加注说明渲染部分是错的。

## 三、18 处旧数字的归类（不全是错）

扫描发现 18 处引用旧值 `44,810` / `2.004`，需分类：

| 类别 | 文档 | 处理 |
|---|---|---|
| **历史记录**（当时确实是 44,810）| P6、P7、P9、P24 | **不改**，它们是过程记录 |
| **修复前后对比**（左旧右新）| P30、P35、P37 | 不改，格式正确 |
| **错误结论** | P8、CONTRACT | **已改** |
| **第三方字体信息** | REBUILD-PLAN（Noto/SHS 版本）| 不改 |

**关键判断：文档里出现旧数字不一定是错，要看它是「历史记录」还是「当前结论」。**

## 四、教训

这与 P37 的「口径混淆」、P41 的「大小相同≠内容相同」是同一条线的第三例：

| 轮次 | 错误直觉 | 正确做法 |
|---|---|---|
| P37 | 数字不同 → 一定有一个错 | 先看口径 |
| P41 | 大小相同 → 内容相同 | 用哈希 |
| **P44** | **出现旧值 → 一定是过时结论** | **先看是历史记录还是当前结论** |

**都要先问「这个数字在文档里扮演什么角色」。**
