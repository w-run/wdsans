# P78：数字宽度与 tnum 特性缺口（受硬约束限制）

## 动机

前面验证了几何与光学，但**数字排版的基础场景**从未检查：

表格、金额、编号都需要**数字逐位对齐**。若数字不等宽，列会错位。

## 一、发现：我们的数字不等宽

| 字体 | 数字宽度 | 是否等宽 |
|---|---|---|
| **我们 Regular** | 362 ~ 587（差 225）| **不等宽** |
| Noto 400 | **全部 521** | **等宽** ✓ |
| OPPO 400 | 407 ~ 611（差 204）| 不等宽 |
| 鸿蒙 400 | **全部 570** | **等宽** ✓ |
| Mona VF | 353 ~ 639（差 286）| 不等宽 |

**只有 Noto 和鸿蒙的数字是等宽的。我们和 OPPO、Mona 都不等宽。**

## 二、关键区别：是否有 tnum 特性

| 字体 | 数字特性 |
|---|---|
| **我们 Regular** | **无** |
| Noto 400 | 无（但默认就等宽）|
| **OPPO 400** | **`pnum` `tnum`** |
| **鸿蒙 400** | **`pnum` `tnum`** |
| **Mona VF** | **`frac` `pnum` `tnum`** |

### 这解释了两条不同路线

| 路线 | 做法 | 代表 |
|---|---|---|
| A. 默认等宽 | 数字字形本身等宽 | Noto、鸿蒙 |
| B. 默认比例 + tnum 开关 | 提供 tnum，用户按需开启 | OPPO、Mona |

**我们两条都不是**：默认比例宽，又没有 tnum 开关。
这是真正的问题。

## 三、根因：合并时丢了 Mona 的数字特性

```
我们的 GSUB 特性:
aalt calt ccmp dlig fwid hist hwid liga ljmo locl pwid ruby tjmo vert vjmo vrt2
数字相关: 无

Mona 的数字特性: frac pnum tnum   ← 全部丢失
```

我们的数字字形名是 `zero` `one` `two` …（来自 Mona），
但**没有 gvar**（说明是静态合并，不是可变插值）。

**Mona 的 `tnum`/`pnum`/`frac` 在拉丁合并时没有被移植过来。**

## 四、能否修复？——受硬约束阻断

### Mona 的 tnum 是怎么实现的

```
tnum lookup type 1，10 条映射：
  zero → zero.tf
  one  → one.tf
  ...
  nine → nine.tf
```

**需要 10 个额外的「等宽数字变体」字形。**

### 我们的字形槽位

```
我们的字形数:  65535
TrueType 上限: 65535
剩余槽位:          0        ← 无法新增任何字形
```

而且：

```
Mona tnum 目标字形数: 10
我们缺失的:          10  (zero.tf, one.tf, ... nine.tf 全部没有)
```

### 结论：**当前无法补充 tnum**

这是 AGENTS.md 第一条铁律的直接后果：
> 只移动节点，不增删节点（基座 65535 已达 TrueType 上限）

补 tnum 需要 10 个新字形，槽位为 0，**做不到**。

## 五、影响评估

| 场景 | 影响 |
|---|---|
| 中文正文 | **无影响**（不含数字列对齐需求）|
| 表格中的数字列 | **会错位**（比例宽 + 无 tnum）|
| 等宽代码/编号 | 不适用（应使用等宽字体）|
| 纯数字展示（如「2026」）| 视觉正常，只是不逐位对齐 |

### 与 OPPO 对比

OPPO 默认也不等宽，但**提供了 tnum 开关**。
在需要对齐时用户可开启。我们连这个开关都没有。

**这是我们相对 OPPO 的一个真实功能缺失。**

## 六、可能的替代方案（评估）

| 方案 | 可行性 | 代价 |
|---|---|---|
| 补 tnum 字形 | **不可行**（槽位 0）| — |
| 删掉某些现有字符腾槽位 | 可行但**代价大** | 违反「不删 cmap」铁律，且破坏覆盖 |
| 独立发布一个「表格版」子集 | 可行 | 需重建，工程量大 |
| CSS `font-variant-numeric: tabular-nums` + 系统回退 | **现实方案** | 数字回退到系统等宽字体 |

### 推荐：记录为已知限制，不做破坏性修复

理由：
1. 中文正文场景无影响（主要用途）
2. 修复需要删字符，违反铁律且破坏覆盖率
3. 表场景可用 CSS 指定等宽回退字体

## 七、结论

| 项 | 结果 |
|---|---|
| 数字宽度 | 362~587，**不等宽** |
| tnum 特性 | **无**（Mona 的在合并时丢失）|
| 能否修复 | **否**（字形槽位 0，需 10 个新字形）|
| 中文场景影响 | 无 |
| 表格场景影响 | 数字列不对齐 |
| 定性 | **已知限制**，非疏漏；受 TrueType 上限约束 |

## 八、教训

### 1. 有些缺陷「发现即终局」

前面几轮发现的缺陷（命名冲突、路径硬编码、OFL 缺失）都能修。

但**这个不能修**——不是不想，是物理上不可能（槽位为 0）。

**区分「可修缺陷」和「受约束的限制」，比发现缺陷本身更重要。**
对后者，正确做法是记录清楚 + 给出替代方案，而不是硬凑。

### 2. 检查时要看「参照字体怎么解决同一个问题」

如果只看我们自己「数字不等宽」，会以为是 bug。

对比后发现两条合法路线（默认等宽 / 提供 tnum），
而我们**两条都没走**——这才是问题所在。

**不是「和别人不一样就是错」，而是「别人都提供了某种能力，我们没有」。**
