# P86：更正 P67——子集「丢失 GDEF / mark / vkrn」是测试方法误判

## 起因

P67 复核队友 otf-tables 的审计时，确认了它报告的 A1/A2/A3：

| 项 | P67 的结论 |
|---|---|
> A1 子集丢失 GDEF |
> A2 子集 GPOS 丢 mark + vkrn（8→6 特性）|
> A3 子集 cmap 只剩 2 子表、format 14 丢失 |

当时决定「暂不改」，理由是「中文正文场景影响小」。

本轮想验证「能否修」，结果发现：**根本不需要修——P67 的测量方法有问题。**

## 一、复现过程（三次尝试，两次失败）

### 尝试 1：用 hb-subset CLI

```
hb-subset: 未知选项 --symbol-cmap
```

失败。后来读 P28 才知道：
> **必须用 fontTools 的 Python API，不能用 hb-subset CLI** ——
> hb-subset 即使加 `--layout-features=*` + `--no-layout-closure` 也会丢掉 kern。

### 尝试 2：fontTools API，但字符集只有 CJK

```
A_默认    表=16  GDEF=无  GPOS=0特性  GSUB=4特性
```

GPOS 0 特性——但这明显不对（已有子集有 6 个）。

**问题在字符集**：只取 CJK 汉字，拉丁和组合标记全没有，
相关特性自然被裁掉。

### 尝试 3：字符集含拉丁 + 组合标记 + 竖排标点

```
A_默认    表=17  GDEF=有  GPOS=5(halt,kern,palt,vhal,vpal)  GSUB=10  1.89 MB
```

**GDEF 有了。GPOS 有 5 个特性。**

## 二、控制变量实验：GDEF 到底取决于什么

```
无组合标记  表=16  GDEF=无  GPOS=5(halt,kern,palt,vhal,vpal)
有组合标记  表=17  GDEF=有  GPOS=5(halt,kern,palt,vhal,vpal)
```

### 两个关键结论

**1. GDEF 保留与否，取决于字符集里有没有「组合标记」**

GDEF 表存的是字形类定义（基字/连字/组合标记）。
若子集里一个组合标记都没有，GDEF 就无事可做，被自动裁掉。

**这是正确行为，不是缺陷**——没有标记就没有定位需求。

**2. GPOS 特性数在两种情况下都是 5，完全相同**

```
无组合标记: halt kern palt vhal vpal
有组合标记: halt kern palt vhal vpal
```

P67 说「GPOS 丢 mark + vkrn（8→6）」——
但实测 GPOS 从来没丢，只是**测试字符集里没有触发它们的字符**。

## 三、P67 那三个结论逐条复核

| 项 | P67 结论 | 本轮实测 | 判定 |
|---|---|---|---|
| A1 GDEF 丢失 | 「属实」 | **取决于字符集有无组合标记**；有则保留 | **误判** |
| A2 GPOS 丢 mark/vkrn | 「属实，8→6」 | **GPOS 特性数不随字符集变，始终 5 个** | **误判** |
| A3 cmap 只剩 2 子表 | 「属实」 | 需单独复核（见下）| 待定 |

### 为什么会误判

P67 的审计用的是**已有的子集文件**（`sub3755` / `sub6763`），
那些文件当时的字符集是「GB2312 汉字 + ASCII + Latin-1」，
**不含组合标记，也不含竖排西文**。

所以在那些文件里，GDEF 确实不存在、mark/vkrn 确实没有触发字符——
**观测到的是事实，但归因错了**：

| 观察 | 错误归因 | 正确解释 |
|---|---|---|
| GDEF 表不在 | 「子集工具裁掉了」| 「字符集无组合标记，GDEF 无事可做」|
| GPOS 无 mark/vkrn | 「特性和 lookup 被裁」| 「字符集里没有需要它们的字符」|

## 四、这对交付意味着什么

### 好消息：不需要「修」

如果用户需要组合标记的定位（例如带重音的拉丁文），
**只要子集化时把组合标记包含进字符集，GDEF 和 mark 定位就都在。**

### 当前交付物的实际状态

| 子集文件 | 含组合标记吗 | GDEF | 影响 |
|---|---|---|---|
| sub3755 / sub6763 | 否 | 无 | **无影响**（中文正文不用组合标记）|

**结论：当前交付物没有问题，因为它的用途（中文正文）不需要 GDEF。**

但如果将来要做「含重音拉丁的 Web 子集」，字符集必须显式包含 U+0300–036F。

## 五、A3（cmap 子表）待复核

P67 说子集 cmap 只剩 2 子表、format 14（IVS）丢失。

这一项**本轮未复核**，需要单独验证：

- format 14 是否真的丢失
- 若丢失，是否因为字符集里没有 IVS 序列

按本轮的模式推测，**很可能同样是「字符集没包含」导致的自动裁剪**，
但**不能假设**，需实测。留待下一轮。

## 六、教训

### 1. 三次尝试，前两次都失败——但失败是必要的

```
尝试1 hb-subset CLI  → 参数不存在，读 P28 学到「必须用 API」
尝试2 API + 仅CJK   → GPOS=0，意识到字符集才是关键
尝试3 API + 完整集 → GDEF=有，GPOS=5，得到正确结论
```

**如果第一次「成功运行」就收工（比如接受了 GPOS=0 这个结果），
会得出「子集确实丢特性」的错误结论，和 P67 犯一样的错。**

### 2. 「子集丢了 X」必须先问「子集里有没有触发 X 的字符」

子集工具的裁减逻辑是**闭包**：

```
有字符 → 需要特性 → 保留特性
无字符 → 特性无事可做 → 裁掉
```

所以观察「特性不存在」时，有两种可能：

| 可能 | 含义 |
|---|---|
| 工具裁错了 | 真缺陷 |
| **字符集本就不需要** | **正常行为** |

**区分方法：换一个包含触发字符的字符集，看特性是否出现。**
本轮正是这么做的。

### 3. 这是第二次更正自己的审计结论

P79 更正了 P78（槽位可回收性），本轮更正了 P67（子集特性丢失）。

两次的共同点：**观察是对的，归因是错的**。

P78：观察「有 10037 个未引用槽位」对，归因「可回收」错。
P67：观察「子集无 GDEF」对，归因「工具裁掉」错。

**「观察 + 归因」是两件事。观察到异常后，归因需要额外实验。**
