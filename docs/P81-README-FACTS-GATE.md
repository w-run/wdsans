# P81：README 事实自动化闸门（第六道）

## 承接 P80 的待办

P80 手动修正了 7 处 README 过时事实，但留下一个问题：
**下次重建后又会过时。**

本轮的根因分析：

| 字段类型 | 举例 | 谁维护 |
|---|---|---|
| 说明性文字 | 「基于 Noto 重构」「笔画减细」 | **人**（很少变）|
| 事实性数字 | 文件数 29、体积 247.6 MB、85 份文档 | **应该由脚本算** |

**把这两类混在一起手写，必然导致后者持续过时。**

## 一、实现：`wds/gen_readme_facts.py`

### 生成能力

```bash
python -m wds.gen_readme_facts
```

输出：

```
### 静态实例
| 文件 | 字重 | usWeightClass | 大小 |
|---|---|---|---|
| WDesignSansSC-Thin.ttf | Thin | 250 | 20.98 MB |
| ... |

### 网页用
| WDesignSansSC-{7档}.woff2 | 对应静态实例，7.48-7.93 MB |
| **WDesignSansSC-VF.woff2** | 可变字体，单文件覆盖 250-900，20.01 MB |

### 合计
文件数 29（含子集与文档）  总体积 247.6 MB  编号文档 85 份
```

### 检查能力

```bash
python -m wds.gen_readme_facts --check
```

逐项比对 README 中的数字与实际产物：

| 检查项 | 方法 |
|---|---|
| 七档 TTF 大小 | 正则提取表格单元格，与 `os.path.getsize` 比 |
| 文件数 | 统计 dist + subset 下的文件 |
| 总体积 | 累加字节数 |
| VF.woff2 大小 | 同 TTF |
| 文档份数 | 数 `docs/P*.md` |

## 二、立刻抓到一个真实偏差

第一次跑 `--check`：

```
!! 文档份数: README 84 != 实际 85
退出码=1
```

**原因**：P80 那一轮写完文档后，`docs/` 变成 85 份，
但 README 里写的是 84。

也就是说：**我在 P80 手动更新的数字，当轮就已经过时了。**

这恰好印证了 P80 的判断——
「人手动维护全局统计数字」这件事，**本身就是不可靠的**。

## 三、阴性测试（必做）

按 P70/P71 确立的原则，新闸门必须有阴性测试。

```python
# 故意破坏三处
txt = txt.replace("20.98 MB", "21.50 MB", 1)      # TTF 大小
txt = txt.replace("文件数        29", "文件数        16", 1)  # 文件数
txt = txt.replace("247.6 MB", "220.4 MB", 1)      # 总体积
```

结果：

```
=== 阴性测试：故意改错 3 处 ===
  !! Thin.ttf 大小: README 21.50 MB != 实际 20.98 MB
  !! 文件数: README 16 != 实际 29
  !! 总体积: README 220.4 != 实际 247.6 MB
检出问题数: 3 -> **有效**

=== 阳性测试：原文件 ===
问题数: 0 -> 正确
```

**三处全部检出，原文件 0 问题。闸门有效。**

## 五、教训

### 1. 「手动更新文档数字」在结构上就是错的

P80 我手动改了 7 处数字，当轮就漏了一处（文档份数）。

不是我不细心——是**这类字段依赖全局统计，而人的注意力总在局部**。

**任何「每次都要重新算」的数字，都不该由人来写。**

### 2. 生成与校验要成对

只做「生成」不够——生成脚本可能被绕过（人直接改 README）。

所以同时提供 `--check`，并接入构建闸门。

| 手段 | 作用 |
|---|---|
| `python -m wds.gen_readme_facts` | 生成正确内容 |
| `--check` + 闸门 | 发现有人绕过了生成 |

### 3. 新闸门立刻就能发现问题，是好兆头

第一次跑就报「文档份数 84 != 85」。

**如果一个闸门装上后从来报不出任何东西，反而要怀疑它是否有效。**
（这也是为什么每道闸门都要做阴性测试。）
