| wght | Noto 横/竖/密度 | 本产物 横/竖/密度 | 竖/横 | 横减细 | 竖减细 |

**减细量在各字重恒定（12.1 / 6.7）**，说明 gvar 正常、字重曲线未被破坏。
横厚在 250→900 全程单调递增，无跳变。

### 验证脚本自身出过两个 bug（都记下来）

**bug 1：用了轴范围外的字重值。**

本产物 axis 是 `(250, 400, 900)`，我最初测 100/200 档，全部被钳到 250，
三个字重读数完全相同（36.0/39.0/0.206），看起来像 VF 损坏。
实际是测试值越界。**先查 axis 范围再测。**

**bug 2：`inplace=True` 污染了对照组。**

```python
# 错：复用同一个 font 对象
for w in weights:
    i = instancer.instantiateVariableFont(f, {"wght": w}, inplace=True, ...)
    # f 被就地修改，下一轮读 SRC 时拿到的其实是 NEW 的数据

# 对：每个字重重新 TTFont(path)
f = TTFont(path)
```

这个 bug 让 SRC 那一列显示了 NEW 的值，差点让我误判成「字体坏了」。

## 2. 「竖/横比调到 1.074」这个目标不存在

我前两轮一直把「把竖/横比从 1.057 调到 OPPO 的 1.074」当待办。**这个待办是错的。**

### 决定性数据

| 字重 | OPPO 竖/横 | HOS 竖/横 |
|---|---|---|
| 400 | **1.074** | 1.058 |
| 500 | **0.970** | 1.019 |
| 700 | **0.992** | 0.986 |

**OPPO 自己也不是恒定的**：400 档竖比横粗 7.4%，500/700 档反而竖比横细。

所以「1.074」只是 **OPPO 在 400 这一个字重上的采样值**，
不是意图贯穿全字库的设计规律。把它当作跨字重的目标值是错的。

### 我们的产物其实是对的

| 字重 | 本产物 | OPPO | HOS |
|---|---|---|---|
| 250 | 1.083 | — | — |
| 400 | 1.057 | 1.074 | 1.058 |
| 500 | 1.050 | 0.970 | 1.019 |

- 400 档：本产物 1.057 ≈ HOS 1.058，低于 OPPO 1.074，**同一量级**
- 400→500 的趋势：本产物 1.057→1.050（降），OPPO 1.074→0.970（降），HOS 1.058→1.019（降）
  **三者同向**

固定绝对减细量（横 12 / 竖 7）自然产生「细字重比值更大」的效果，
恰好与参考字体的趋势一致。**不需要调。**

## 3. 累计被推翻的判断（诚实记录）

| # | 我原本的判断 | 实测结论 |
|---|---|---|
| 1 | 改 gvar delta 能改默认实例 | 不能，要改 glyf base |
| 2 | 等比缩放会改变墨密度 | 不会，比例不变 |
| 3 | 出脚 = 低于基线 | 四字体都下探，OPPO 更深 |
| 4 | 出脚 = 细长竖条顶端 | 明 c5 顶 = c0 顶，同高 |
| 5 | 出脚 = 轮廓间关系 | 是单一轮廓内的 ⊓ 形开口 |
| 6 | 折角微圆 8–14u | 648 个角点全 90°，不存在 |
| 7 | 竖/横比要调到 1.074 | OPPO 自身随字重变化，无反义单一目标 |

**7 条里有 7 条被推翻。** 这不是效率问题——每一条都是靠实测救回来的，
没有一条是靠推理发现的。这印证了 AGENTS.md 的「数值测量不能代替看图」，
以及它的反命题：**看图也不能代替测量**。
